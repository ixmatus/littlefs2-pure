## What this crate is

A pure Rust implementation of the LittleFS v2 filesystem, suitable for embedded targets and as a host side mount tool. The downstream consumer in this development tree is Parnell's SMIL calculator firmware project; the crate is general purpose.

LittleFS v2 is the [official on disk format](https://github.com/littlefs-project/littlefs/blob/master/SPEC.md) used by the C reference at `littlefs-project/littlefs`. The spec is the oracle; the C reference is the behavioral oracle for everything the spec does not pin down to bit level.

## Verification posture

The crate is held to ferrodec's four stack model. Each stack catches a class of failure the others miss. See `docs/decisions/0003-verification-stacks.md` for the full argument.

1. **Unit tests** inside `src/*.rs` for tight per module invariants.
2. **Property tests** (`tests/property_*.rs`, proptest) for surface level invariants that should hold over arbitrary inputs. CRC byte-by-byte versus slice. Tag encode then decode is the identity. Storage reads after writes return what was written.
3. **Conformance** (`tests/conformance.rs`, when it lands) against committed golden vectors generated by the C reference. Per file expected (passes, skips) table, no aggregate pass floor. Any silent trade off becomes a hard failure.
4. **Kani harnesses** (`src/verify/`, behind `--features=kani`) for totality properties that fuzzing cannot reach. Tag classification dispatch, CRC bounded slice match against the bit by bit reference, metadata commit accept or reject totality.
5. **Fuzz** (`fuzz/`, cargo-fuzz, later) for parser totality on adversarial byte sequences.

A property test compares against an oracle, not just a self consistency invariant. The CRC table implementation is checked against a bit by bit reference. The tag bit layout is checked against hand crafted vectors and against the C reference once the conformance harness lands.

## Engineering notes specific to this crate

### Bit accuracy is non negotiable

The on disk format must match the C reference byte for byte. Every tag field, every CRC, every revision counter must produce the same disk image the C reference would. When in doubt, generate a vector with C littlefs and check ours against it.

### Storage trait is the only hardware boundary

The `Storage` trait abstracts read / program / erase / sync. Everything above it is generic in `S: Storage`. No `std::io`, no `embedded-hal` versions, no global allocator dependence inside the kernel. Hosts that want `std::io::File` backing wrap their handle in a `Storage` impl; the wrapper is the only place that knows about std.

### No allocator in the kernel

The kernel never allocates. Fixed size caches (read, program, lookahead) live in the `Storage` impl or are passed in. `alloc` and `std` features add convenience wrappers around the no_alloc core; they never become a hidden dependency of the kernel.

### XOR encoded tags

LittleFS stores each tag XORed against the previous tag in the same commit. The "previous tag" for the first tag in a block is the all ones value (`0xFFFFFFFF`), which makes a freshly erased region (`0xFF` bytes) decode as the tag value `0x00000000` after XOR, and that value has the valid bit clear, so an erased region naturally reads as "no more tags." Keep this invariant present when reasoning about commit boundaries.

### Revision counter wraparound

Each metadata pair carries a u32 revision counter. The active block is the one with the higher counter, where "higher" is the modular comparison `(a - b) > 0` reinterpreted as i32 sign. Naive `a > b` would break at the 2^32 wrap. The C reference uses `(int32_t)(a - b)`; the Rust translation uses `i32::wrapping_sub` and checks the sign.

### Path is fixed capacity

LittleFS caps path components at 255 bytes (`LFS2_NAME_MAX`). The crate's `Path` type holds a fixed capacity buffer, never heap allocates, and validates on construction.

## What "done" means here

A v1.0 release requires all of the following:

- Superblock detection, mount, and format.
- Directory traversal: open, read, walk, close, mkdir, remove, rename.
- File operations: open, read, write, seek, truncate, close.
- Persistence: commits land atomically; mid commit power loss leaves the previous state intact.
- Conformance harness passes against C reference vectors at zero failures.
- Property tests cover the read and write surface end to end.
- Kani harnesses cover tag totality, CRC bounded inputs, and the commit accept or reject dispatch.
- `cargo build --target thumbv6m-none-eabi --no-default-features` succeeds.
- `cargo clippy --all-targets -- -D warnings` is clean.
- `KNOWN_ISSUES.md` lists every gap against the spec; the list is empty at v1.0.

Stay in 0.x until every item above holds. Label every 0.x release with the gap list in `CHANGELOG.md`.

## When to spawn a sibling crate

Conformance has a heavy build (the C reference must compile in CI). When that lands it becomes `littlefs2-pure-conformance` as a workspace member, so the main crate's dev dependencies stay small. Until then the conformance runner can live in `tests/` with vectors committed at rest. This mirrors ferrodec ADR-0011's flat workspace pattern.
