# ADR-0003: Four verification stacks, each catching what the others miss

- **Status**: accepted
- **Date**: 2026-05-10

## Context

A filesystem is the kind of artifact where a silent bug costs months. Wrong bytes on disk look fine until the user reaches for the data and finds it gone. The C reference has been hardened by a decade of production deployment; we cannot replicate that pedigree by chance. We replicate it on purpose, by layering verification stacks so a bug has to evade every layer to ship.

ferrodec's six agent review (ADR-0010) listed the failure modes that single-layer verification missed: the special case that no test enumerated; the long input that the test happened not to exercise; the pinned wrong behavior; the regression that a one sided pass floor hid. Each of those was caught by a layer the original test set lacked.

## Decision

Five stacks, each in a defined slot, with an explicit claim about what it catches.

### Stack 1: unit tests inside `src/*.rs`

Per module invariants too narrow for the property surface. The CRC of a known three byte input. The tag byte order of a known constructed value. The error variant a known invalid path produces. Unit tests are fast feedback during development; they do not protect against unforeseen inputs.

### Stack 2: property tests in `tests/property_*.rs`

Each file checks a surface level invariant against an oracle, not a self consistency check.

- `property_crc.rs` — the table CRC matches the bit by bit reference over random byte slices.
- `property_tag.rs` — every `Tag` constructed by the public API encodes and decodes back to itself, and every random `u32` either decodes to a valid `Tag` or is rejected.
- `property_storage.rs` (Phase 1) — `read` after `program` returns the programmed bytes; `erase` returns the block to `0xFF`.
- `property_metadata.rs` (Phase 1) — committed tags reappear when the metadata pair is reread.

A property test must compare against an oracle. The CRC table is checked against the bit by bit polynomial. The metadata reader is checked against the C reference output (Stack 3). A self consistency check that does not catch a 1 ULP regression is not a property test; it is a sanity check.

### Stack 3: conformance vectors in `tests/conformance.rs`

Committed disk images generated by the C reference at `tools/gen_vectors.sh`. The runner reads each image, walks it, and asserts byte equality against the expected listing.

Per file expected `(passes, skips)` table, no aggregate pass floor. A silent trade off (file A gains, file B loses, total unchanged) becomes a hard failure. This is the exact pattern ferrodec ADR-0010 establishes after finding that an aggregate floor masked the FMA bug fix from being a forced "fix or regress" choice.

### Stack 4: Kani harnesses in `src/verify/`

Behind `--features=kani`. The harnesses prove totality properties that fuzzing cannot exhaust:

- `tag::classify` is total over all `u32` inputs and never panics.
- `crc::update` over a 16 byte symbolic slice matches the bit by bit reference exactly.
- Metadata commit acceptance is the projection of "CRC matches" on the symbolic commit header; no input lands in an undefined dispatch.
- (Phase 3) Revision counter comparison is totally ordered modulo wrap.

Bounded inputs are an honest constraint, not a hidden gap. Each harness documents what it does and does not prove in its module doc; future readers do not infer "Kani proven" guarantees beyond the actual claim.

### Stack 5: libFuzzer harnesses in `fuzz/`

A separate crate (`fuzz/Cargo.toml`) so cargo-fuzz's nightly dependency stays out of the main crate's lockfile. Targets:

- `parse_tag` — feed arbitrary `u32` to `Tag::from_bits_unchecked` followed by `classify`, assert no panic.
- `walk_metadata` — feed an arbitrary byte sequence as a metadata block, assert the walker either returns a complete tag list or a clean error.
- (Phase 3) `mount_image` — feed an arbitrary byte sequence as a whole filesystem image, assert mount either succeeds or fails with a typed error.

Each fuzz target produces corpus and crash directories on disk. Reproducers from crashes are promoted to unit tests in Stack 1.

## Consequences

**Wins.**

- Bugs that survive one stack are usually caught by another. Property tests find input shapes unit tests forgot. Conformance pins the bit accurate truth. Kani exhausts the totality dispatch. Fuzz finds adversarial parser inputs.
- The verification surface is a deliverable, not an afterthought. A new module ships with property tests against the surface and (where applicable) a Kani harness in the same change.

**Costs.**

- Five stacks demand discipline. A new feature in `src/` without corresponding tests is not done.
- Conformance vectors need regeneration tooling. The cost is one shell script and a committed C reference checkout (or a pinned tarball); it pays for itself the first time a parser bug ships.
- Kani harnesses are slow to write. The budget is two hours per harness; over budget, the harness is deferred and documented in KNOWN_ISSUES.

**Explicitly out of scope.**

- Verus or Creusot. ferrodec ADR-0004 skipped Verus graduation; we inherit that choice. If the v2.x of this crate adopts a richer prover, that is a future ADR.
- Mutation testing. A useful tool, not a v1.0 gate.
